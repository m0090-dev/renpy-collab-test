# 共通ルール（核）

プロジェクト固有の事情は `docs/PROJECT.md` に書く。このファイルはどのプロジェクトでも
ほぼそのまま使える核の部分だけ。

## 1. 進行

- 作業の流れ: 作業ブランチで作る → 報告 → 権限者が push/マージ → 自動で公開 → 実機で確認。
- 設計と進行の正本はこのリポジトリの `docs/`。

## 2. 命名

- コードは、その言語の標準的な慣習に統一する（例: Python なら PEP 8）。
- スクリプト系は、使用ツールの慣習に統一する。
- ブランチ名は英小文字とハイフンのみ（公開 URL に対応させるため、`/` は使わない）。

## 3. 編集の作法

- 編集したら必ずコメントか変更メモを残す（何を・なぜ変えたか）。
- ファイルは扱いやすい単位に分割する。1 ファイルに全部を詰めない。
- 自動チェック（lint / test 等）が通る状態を保ち、テスト可能な構造にする。

## 4. 他人のコード・素材

- 他人のコードを無断で使わない。
- 公開ライブラリを使う場合はライセンスを確認し、クレジットを明記する。

## 5. 公開と容量

- 本番は main をマージしたときだけ更新する。作業ブランチはテスト公開として分ける。
- ホスティングの上限（容量・帯域など）は `PROJECT.md` に記録し、上限に近づいたら
  古いテスト公開の削除 → 素材の圧縮 → ホスティング分割、の順で対応する。
- マージ済みブランチは削除し、その公開分も消す。

## 6. main の保護（対応するホスティングで設定）

- マージには PR が必要。force push 禁止。ブランチ削除禁止。
- 自動チェックが通らないとマージできない。
- リリースタグは削除・書き換え禁止。

## 7. 報告の型

- 結論から。専門用語は最小限にし、使う場合は一言で説明を添える。
- 選択肢がある場合は、平易な言葉でトレードオフを示して提示する。
- エラーは「何が起きたか＋どうすればいいか」で説明する。
- 動きやタイミングが要点の確認では、文章だけでなく動画やスクリーンショットを添える。
